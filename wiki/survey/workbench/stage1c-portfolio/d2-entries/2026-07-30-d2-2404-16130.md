## 1. 方法本质

GraphRAG 把"全局性提问"（whole-corpus sensemaking，如"这批语料的主要主题是什么"）重新定义
为 query-focused summarization 而非检索问题，于是把跨文档聚合的算力**整体前移到索引期**：
冻结 LLM 逐 chunk 抽实体/关系/claim 并写描述，同名实体合并成图（关系重复次数=边权），再用
Leiden 递归社区检测得到一棵互斥且完全覆盖的社区层次树，自底向上让 LLM 为每层社区写"报告式
摘要"（下层摘要在上层超预算时替换掉更长的元素摘要）。查询期完全不做匹配：选定层级 L 后把该
层**全部**社区摘要随机打乱切块，map 阶段并行生成局部答案并让 LLM 自评 0–100 helpfulness
（0 分丢弃），reduce 阶段按分数降序填满上下文生成全局答案。机制要点是"用图的 modularity
把语料切成主题分区"，而不是"用图做多跳游走"——后者是同期其他工作的路线（§2.2 明确划界）。

## 2. key-value 与三轴定位

- **key 是什么**：在论文评测的管线里，社区摘要**没有 key**。没有任何向量/关键词与 query
  做匹配；层级 L 是配置项（C0/C1/C2/C3 四个并列条件被逐一评测），不是 query 决定的。唯一
  的"选择"发生在 value 已经进过上下文之后（map 阶段的 helpfulness 自评分）。索引期确实造出
  了层次结构，但那是 **value 的层次**，不是 key 的层次。key 侧升级（"embedding-based
  matching of user queries and graph annotations"）被论文明确列为 **future work**
  （§6.2，正文第 441–443 行），并连带提出 roll-up / drill-down 两个未实现的规划机制。
- **value 是什么**：三层并存——原文 chunk（600 token，overlap 100）、元素摘要（实体/关系/
  claim 的 LLM 描述）、社区报告摘要（C0 根层最粗、C3 叶层最细）。value 是**预聚合、抽象化**
  的：实体/关系/claim 抽取被作者自称为 abstractive summarization，即 value 里含原文没有显式
  写出的命题。
- **供给侧决策**：只有两个旋钮，且都不是 query 条件的——(i) 走哪一层社区（C0–C3）；(ii) 上
  下文窗口大小（实测 8k 优于 16k/32k/64k）。没有触发/停止/预算决策，没有"要不要检索"的门。
- **使用侧决策**：map-reduce 的 helpfulness 自评分 + 降序填满，是 value **进过上下文之后**
  的取舍（post-call），不是采集门（pre-call）。这一点对 R2 的"两道门"词典很关键：GraphRAG
  只有第二道门。
- **三形式归属**：组织形式=图+社区层次（强）；供给形式=退化（无 key、无匹配、无规划）；使用
  形式=固定 map-reduce + 自评分排序（中）。

## 3. 主实验数字（逐个核对 LaTeX 源）

评测协议：persona 驱动生成 125 题/数据集（K=M=N=5），LLM-as-judge 头对头胜率，每对比较重复
5 次取平均；四维=comprehensiveness / diversity / empowerment + **directness 作为反向 control
criterion**（作者明说"不应有方法四维全赢"）。判据模型为 GPT-4 系（正文只写 GPT-4 /
gpt-4-turbo）。

1. **Fig. 3（`fig:relativemeasures`）全局 vs 向量 RAG（SS）**：comprehensiveness 胜率
   Podcast 72–83%、News 72–80%；diversity Podcast 75–82%、News 62–71%。其中 C0（根层）
   vs SS = 72%（两个数据集都是 72）；C3 vs SS = 79%/79%；纯文本 map-reduce（TS）vs SS =
   83%/80%（**TS 是 comprehensiveness 的总冠军，不是 GraphRAG**）。
2. **Table 5（`tab:stats_analysis`，附录）显著性**：Podcast C0 vs SS 均值 71.92 : 28.08，
   Z=−6.2，Holm-Bonferroni 校正后 p<.001；C2 vs TS 57.28 : 42.72，p<.001。
3. **Table 2（`tab:community summaries`）查询期 token 成本**：Podcast C0 = 34 个社区摘要 /
   26,657 tokens（TS 的 **2.6%**）；News C0 = 55 / 39,770（**2.3%**）；C3 = 746,100（73.5%）
   / 1,140,266（66.8%），即比 TS 省 26–33%。TS 基线 1,014,611 / 1,707,694 tokens。
   → "9x–43x 更少 token"的说法出自本表标题。
4. **索引期成本**：Podcast（≈1M tokens，1669 chunk）图索引耗时 **281 分钟**，16GB RAM /
   Xeon 8171M 虚机 + 公有 OpenAI `gpt-4-turbo` 端点（2M TPM / 10k RPM）。图规模：Podcast
   8,564 节点 / 20,691 边；News 15,754 节点 / 19,520 边。
5. **Table 3–4（Claimify 声明级复核，Experiment 2）**：平均声明数 News C0 **34.18** vs
   SS **25.23**、Podcast C2 **32.46** vs SS **26.50**（全部 p<.05）；聚类数（diversity）
   News@0.5 C0 **23.42** vs SS **17.92**。LLM 判定与声明级判定在非平局子集（占
   33%/39%）上一致率 78%（comprehensiveness）/ 69–70%（diversity）。
6. **附录 C（`app:window`）上下文窗口**：8k 在 comprehensiveness 上**普遍优于** 16k/32k/64k
   （平均胜率 58.1%），diversity 52.4%、empowerment 51.3% 与更大窗口持平。
7. **附录 B（`fig:chunkentities`）self-reflection gleaning**：HotPotQA 上 600-token chunk
   的实体引用数 9,348（0 轮）→ 15,976 → 19,491 → 27,240（3 轮）；2400-token chunk
   5,761 → 19,433。同 gleaning 轮数下 600 token 抽出的实体引用约为 2400 token 的两倍。

## 4. DFS 四问

**方法**：把跨文档聚合从 query 时搬到索引时，用图的模块性（Leiden 社区）而不是相似度做语料
分区，再用递归摘要把"全局视图"物化成可直接消费的 value。核心洞察是"全局问题不是检索问题"，
因此评测面也从 recall 换成生成质量胜率。

**局限**：(i) 查询期没有 key、没有 query 条件路由，任何 query 都要吃掉整层摘要——C0 便宜是
因为层很小（34/55 个），不是因为选得准；(ii) empowerment 维度结果混杂，作者自己归因于摘要
化丢掉了"具体例子、引文、原话"；(iii) 只在两个 ≈1M/1.7M token 语料上验证，作者承认泛化性
与 fabrication rate（如 SelfCheckGPT）未测；(iv) 增量更新代价未讨论——新文档进来社区层次要
重算（这一点被 LightRAG 抓住并量化）；(v) 实体消歧用精确字符串匹配。

**改进空间**：论文自列的 future work 就是 R2 关心的位置——用 embedding 把 query 匹配到图注解
（即**给社区摘要造真正的 key**）、just-in-time 社区报告生成、跨层 roll-up 与顺着
"information scent"的 drill-down。这三件**在这篇论文里都没做**，因此"query 条件的层次路由"
在本篇上是**空位**，不是占据。

**可借鉴**：(a) directness 作为反向 control criterion 的判据设计（防"四维全赢"的假象），
R2 §6/§7 应直接抄；(b) helpfulness 自评分 + 降序填满上下文，是零训练、纯 prompt 的 post-call
证据取舍，可作 R2 使用侧的冻结基线；(c) 8k > 64k 的实证，直接支持 R2 不把"更长上下文"当默认
更优；(d) gleaning（自反思补抽）作为库预处理期的免训练召回提升手段。

### 深读后新增的、R2 应该知道的事实

1. **方法位空缺而非被占（对 R2 有利）**：GraphRAG 论文没有做"query 条件的层次/多面 key
   路由"，反而把它写成 future work。R2 §3.4 的 O2 多面 key + query 面路由在**本篇上**是
   空位；但注意占据判定不能只看这一篇——见 HippoRAG 条目（uncertainty ensemble = 多面 key
   融合已被占）与 LightRAG 条目（双路关键词路由已被占）。GraphRAG 真正占据的是"索引期把
   跨文档聚合物化成层次 value"。
2. **audio 适用性线索（重要）**：GraphRAG 主实验两个语料之一是 **Podcast transcripts**
   （*Behind the Tech with Kevin Scott* 公开转写，1669×600 token ≈1M token）。也就是说
   **文本域的图/社区组织已经在口语转写语料上被验证过**，且在该语料上的胜率与新闻语料同量级
   （72–83% / 75–82%）。这同时给 R2 两个抓手：(a) "图组织能不能吃口语数据"已有正面证据，
   R2 不必重新论证；(b) 该验证只用了**转写文本**，声学/副语言面完全没有进 key 或 value——
   R2 §3.3 说的语音域空位在这里得到反面印证，且 O2 多面 key 的空位正落在这条缝上。R2 §3.1
   现在把 GraphRAG 纯粹当"文本域"证据，漏掉了"其主语料本就是语音转写"这一有利事实。
3. **可搬的冻结组件**：(a) Leiden 递归社区检测（graspologic 库）纯图算法、无训练；
   (b) 社区摘要模板 + 按 (source+target degree) 降序的元素优先级填充策略；(c) map 阶段
   0–100 helpfulness 自评分 + reduce 降序填充；(d) gleaning 自反思补抽（logit bias=100
   强制 yes/no）。四者都是 prompt/算法级，符合 R2 "冻结 LLM 仅做库预处理期结构抽取"的红线
   ——但注意 (c) 发生在作答期，若 R2 采用需按红线归入"使用侧"而非"预处理期"。
4. **成本记账的文本域参照数**：索引 281 分钟 / ≈1M token 语料（gpt-4-turbo）；查询期
   C0 = 26,657 tokens/query（TS 的 2.6%）。R2 §6.5 九维成本记账可直接引这两个数作为"图组织
   构建代价 vs 查询代价"的量级基准。
5. **与 LightRAG 的矛盾证据（R2 应并列而非单引）**：GraphRAG 把 empowerment 的混杂结果归因
   于"摘要化丢失具体例子/引文/原话"，暗示**原文 value 有不可替代的作用**；LightRAG 的
   -Origin 消融却显示去掉原文 chunk 不掉分甚至更好。R2 §3.4 在设计语音域 value（原始转写段
   vs 冻结 LLM profile）时必须把这两条并列为待裁矛盾，不能只引一边。
