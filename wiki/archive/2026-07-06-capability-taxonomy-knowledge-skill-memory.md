# 能力补齐三分类:知识 / 技能 / 记忆

> **目的.** 冻结的多模态模型可以通过三类 agentic 元件补齐自身能力。本文钉死这三类的定义、边界、对象结构与正确对标类,作为后续所有工作的**术语基准**——防止再把"知识"叫成"记忆"这类概念混淆(§5 记录了正是这个混淆已经发生在两份 WS-A 文档里)。

## 1. 三类能力(模型缺什么 → agentic 怎么补)

| 模型缺的东西(粒度) | 名称 | 一句话 | 补的机制 | new-info 类型 |
|---|---|---|---|---|
| 一条**通用事实/内容**(没学过的知识) | **知识 Knowledge** | "什么是真的" | 注入外部事实(query → 相关事实) | 声明性事实 |
| **一类任务的处理程序**(没学过怎么做的任务),用标准模板注册 | **技能 Skill** | "怎么做某一类任务" | 把一个任务能力用标准模板注册给模型(SKILL.md / 工具声明) | 程序 / 能力 |
| **眼前这个具体、处理不了的样本**(没见过的样本) | **记忆 Memory** | "这个具体样本/案例该怎么办" | 召回一个**相似的旧样本 / 解法 / 范例** | 实例级案例 |

**对齐关系(注意不是字面顺序):** owner 描述的"①补知识内容 / ②补任务(模板注册) / ③补处理不了的样本"分别 = **①知识 · ②技能 · ③记忆**。②是技能(不是记忆),③是记忆(不是技能)。

## 2. 区分原理(唯一判据 = 缺失的"粒度")

定位时问三个问题:
- 缺的是**一条通用事实**吗? → **知识**
- 缺的是**做某一类任务的 how-to**(能注册成模板、能复用于该类的所有实例)吗? → **技能**
- 缺的是**处理眼前这一个具体样本**的能力(需要一个相似的具体案例来救)吗? → **记忆**

**关键分野:知识 / 技能是"通用的"**(跨很多实例复用:知识=跨 query 的事实,技能=跨实例的任务程序);**记忆是"实例特定的"**(只对相似的那个具体样本相关)。

## 3. 三者都是 new-info 元件,但补的信息种类不同

三者都能越过 InfoBoundary 的 oracle@N 天花板(都注入了冻结模型自身没有的信息,故属 new-info 元件而非 read-out 编排)。区别只在**信息种类**:知识=事实,技能=任务程序,记忆=实例案例。**⇒ 三者不可互相替代,也不能混为一谈。**

## 4. 各自的对象结构 + 正确对标类

| 元件 | key(按什么检索/触发) | value(存/给什么) | 正确对标的业内系统类 |
|---|---|---|---|
| **知识** | query → 相关事实 的语义匹配 | 外部事实 / 知识条目 | RAG / 知识库 / GraphRAG / WavRAG / SpeechRAG / (拟议的 MMWiki) |
| **技能** | **任务类型**匹配(何时该调用这个技能) | 任务处理程序 / 模板 | SKILL.md / 工具调用 / function-calling / 技能库 |
| **记忆** | **实例相似度**(这个样本像哪个旧样本) | 一个**具体旧案例**(+ 当时怎么处理) | episodic / case-based memory / mem0 / MemGPT / Generative-Agents(**召回自身历史**) |

> **一个反讽(见 §5):** 表里"记忆"那一列的对标系统(mem0/MemGPT/…)正是两份 WS-A 里被拿来对比的 11 个系统——但那些其实是**记忆**的对标类,却被用来判定一个**知识**设计的净新。

## 5. 反思:2026-07-06 两份 WS-A 文档存在概念混淆(dated re-grade,不改原文)

对象 = `2026-07-06-memory-systems-organizational-comparison.md` 与 `2026-07-06-memory-what-to-validate.md`。

**混淆的根源(不全是本轮的锅):** LOCKED 设计 `2026-07-05-omni-multimodal-memory-design.md` 把一个"注入外部知识"的东西命名为"multimodal **MEMORY** system",而它的 value = `{(task,language)→外部知识文本}` —— 按 §1,那**就是知识(①),不是记忆(③)**。两份 WS-A 忠实继承了这个错名。

**由此产生的、需要更正的结论:**
1. **对标类错(约 6 成对错了类).** 对比拿我们的设计对标 11 个"记忆系统",但其中 7 个(mem0/MemGPT/Zep/Generative-Agents/LangMem/A-MEM/Cognee)是**召回自身历史(个性化)**的 episodic 系统——恰是"注入外部知识"的**相反极点**(该文档自己的 provenance 轴 #7 已写明这一点!)。知识元件的正确对标是 RAG / 知识库(WavRAG / SpeechRAG / audio-native KG / GraphRAG),这类只占 11 里约 3 个。
2. **净新判定其实是"知识"的净新(帧错、判对).** §3 判的是"跨模态 speech-key→text-VALUE 存储 + task×lang dict + 训练无关奖励选择"的净新——这本质是**知识检索/组织**的净新(WavRAG 是知识-RAG,是对的比较对象;`{(task,lang)→text}` 是知识组织=MMWiki 的结构)。判定多数成立,但**应归档到知识轨,不是记忆**。
3. **验证契约错标.** H0(外部知识 headroom)、H1(音频 key vs 转写 key 检索知识)是**知识**主张;pillar (d)(训练无关 RL 选择)是**知识选择**的净新。有效,但都属知识轨。
4. **最严重的漏:记忆(③)与技能(②)根本没被分析.** 真正的**记忆**是"按实例相似度召回一个具体旧案例",key 与 value 都是**实例级**——和我们做的(按 query 检索通用事实)是两种东西,未触及。**技能**之前被"折进感知"否掉过,但那用的是**信号触发激活**的定义,**不是** owner 现在的**任务模板注册**定义——所以技能也需在新定义下重看。

**若不纠正会导致的错误:** 我们会建一个"知识引擎"、管它叫"记忆"、按"记忆"去验证它,然后误以为"记忆已搞定"——而**实例召回记忆**和**任务模板技能**一根毛都没碰。net-new 卖点 (d) 是真的,但它是**知识选择**的净新;把它当"记忆"贡献声称,就是错的结论。
